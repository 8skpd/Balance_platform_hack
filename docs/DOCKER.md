# Развёртывание в Docker

Контейнеры содержат собранный интерфейс, Python и зависимости. На машине нужны Docker Engine с Compose v2.20+ и Linux x86_64/arm64 с Landlock ABI ≥ 3. Рекомендуемая основа — Ubuntu 24.04+; для Docker Desktop эти требования относятся к Linux-ядру его виртуальной машины. При несовместимом ядре запуск останавливается с пояснением, исполнение Python без изоляции не включается.

Для обычных расчётов начните с 4 CPU, 8 ГБ RAM и 20 ГБ свободного диска. Это ориентир, а не гарантированный предел: большие наборы и параллельные расчёты потребуют больше памяти и места. На небольшой машине уменьшите `BALANCE_WORKER_CONCURRENCY` и `BALANCE_NORMALIZATION_WORKERS` до 1. При первой сборке необходим доступ к Docker Hub, npm, PyPI и Debian apt.

## Чистая Ubuntu / Debian

Распакуйте исходники, перейдите в корень проекта. Если Docker ещё не установлен:

```bash
sudo ./scripts/install-docker.sh
```

Скрипт использует официальный apt-репозиторий Docker, устанавливает Engine, Buildx и Compose, включает Docker после перезагрузки. Если обнаружены конфликтующие пакеты, он остановится и не будет удалять их самостоятельно. Для других ОС используйте [инструкцию установки Docker](https://docs.docker.com/engine/install/); установка Ubuntu сверена с [официальной инструкцией](https://docs.docker.com/engine/install/ubuntu/).

```bash
cp .env.docker.example .env.docker
sudo ./scripts/docker.sh up
sudo ./scripts/docker.sh admin
```

Последняя команда интерактивно запрашивает логин, имя и пароль первого администратора. Пароль не отображается и не передаётся в аргументах процесса. Повторное создание первого администратора запрещено; остальных пользователей создавайте через интерфейс администрирования. Публичной регистрации нет.

Сайт: **http://127.0.0.1:8080**. Если ваш пользователь уже имеет доступ к Docker, команды можно выполнять без `sudo`. Команда `up` собирает образ и ждёт готовности всех сервисов. Установить Python, Node.js, PostgreSQL или Redis на хост не требуется.

Для доступа с других машин укажите в `.env.docker`:

```dotenv
BALANCE_HTTP_BIND=0.0.0.0
BALANCE_HTTP_PORT=8080
```

После этого выполните `./scripts/docker.sh up`; сайт будет доступен по IP сервера. За HTTPS-прокси дополнительно установите `SESSION_COOKIE_SECURE=1`. Не включайте этот параметр при обычном HTTP: браузер не передаст cookie сессии.

## Состав

| Сервис | Назначение | Постоянные данные |
|---|---|---|
| `app` | FastAPI, интерфейс, API | Общий том `run_data` |
| `worker` | Celery, импорт, расчёты, Python, запросы ИИ | Тот же `run_data` |
| `dispatcher` | Доставка и восстановление задач | Тот же `run_data` |
| `redis` | Брокер очереди, AOF | Том `redis_data` |

SQLite, датасеты, загрузки, отчёты, настройки, аккаунты и резервные копии лежат в `/app/var` общего тома. Это конфигурация для **одного Docker-хоста**. SQLite выбран для совместимости с существующим резервированием базы и файлов вместе. Старый Docker-шаблон с PostgreSQL не мигрируется автоматически: перед его заменой отдельно перенесите данные. Локальная папка `var/` также не подключается автоматически — контейнерная установка начинает с пустого тома.

Redis не публикует порт на хост. API и обработчики запускаются от UID/GID 10001 без Linux capabilities; `no-new-privileges` включён. В `docker/seccomp.json` сохранён [стандартный профиль Moby](https://github.com/moby/profiles) с единственным изменением: разрешены `landlock_create_ruleset`, `landlock_add_rule`, `landlock_restrict_self`. Исходный commit и SHA-256 записаны в `docker/seccomp-source.json`, лицензия — в `docker/SECCOMP-LICENSE`. Внутри процесса пользовательского Python дополнительно действуют Landlock, собственный seccomp и лимиты ресурсов приложения. Режимы `privileged` и `seccomp=unconfined` не используются.

Образ собирается из исходников. Локальные аккаунты, датасеты, `.env`, архивы организаторов и готовые локальные сборки исключены из контекста. Датасет загрузите через интерфейс после входа.

## Ollama

По умолчанию используется существующий сервер `http://192.168.1.76:11434` и модель `qwen3-server:latest`. Для другого сервера измените `.env.docker` перед запуском или «Администрирование → Подключение к ИИ» после входа. Сохранённые в интерфейсе настройки имеют приоритет над переменными окружения.

Если Ollama работает на Docker-хосте, можно указать `http://host.docker.internal:11434`; Ollama должна слушать адрес, доступный контейнерам. `127.0.0.1` внутри контейнера означает сам контейнер. Ollama не входит в Compose: используется ваш отдельный сервер. Недоступность ИИ не мешает основным расчётам и не блокирует старт приложения.

## Управление

```bash
./scripts/docker.sh status
./scripts/docker.sh logs
./scripts/docker.sh logs worker
./scripts/docker.sh down
./scripts/docker.sh up
```

`up` пересобирает приложение и применяет настройки. `down` удаляет контейнеры и сеть, сохраняя тома. **`docker compose down -v` удалит также данные**; обычный скрипт остановки этот флаг не использует. Для обновления исходников выполните `up` снова. Перед обновлением завершите активные задания; при прерывании обработчика штатный механизм очереди обнаружит потерянную задачу после запуска.

Перезапуск Docker на уровне ОС поднимает сервисы по политике `unless-stopped`. Контейнеры, остановленные вручную, запускайте командой `up`. Проверки готовности диагностируют отказ, но сами по себе не перезапускают зависший, ещё работающий процесс; проверьте логи и перезапустите соответствующий сервис.

Резервную копию создавайте и проверяйте через «Администрирование → Резервные копии». Она включает SQLite и файлы из общего тома. Скачайте ZIP на другую машину. Вариант из консоли:

```bash
docker compose --env-file .env.docker exec app python /app/scripts/backup.py create
# Подставьте archive_id из результата предыдущей команды:
docker compose --env-file .env.docker exec app python /app/scripts/backup.py verify --archive /app/var/backups/ARCHIVE_ID.zip
```

## Диагностика и проверка развёртывания

```bash
docker compose --env-file .env.docker config --quiet
docker compose --env-file .env.docker ps
docker compose --env-file .env.docker exec app python /app/docker/runtime_check.py
```

Если `up` не дождался готовности, используйте `./scripts/docker.sh logs`. Частые причины: занятый HTTP-порт, недостаток памяти, недоступные реестры при сборке или запрет Landlock ядром/runtime. При проблемах с Landlock проверьте ядро и подключение `docker/seccomp.json`, не отключайте изоляцию.

Полная проверка выполняется отдельной командой:

```bash
sudo ./scripts/docker-smoke.sh
```

Она создаёт отдельный Compose-проект с временным HTTP-портом и отдельными томами. Проверяются импорт двух заявок, очередь, три пользовательские Python-процедуры, Python-проверка, сводная, HTML-отчёт и восстановление резервной копии через API. Затем контейнеры удаляются и создаются снова, проверяются сохранённая сессия, датасет и отчёт. В конце удаляются только тестовый проект и его тома; рабочая установка не используется. Проверка требует сборки образа, но не требует Ollama.

Конфигурация проверена Compose CLI; проверочный сценарий также прогнан на изолированных локальных API/Celery/Redis. Позднее пользователь подтвердил **успешное развёртывание в Docker и прохождение `scripts/docker-smoke.sh` на своей целевой машине**. Характеристики этого окружения и протокол запуска в репозитории не опубликованы. При развёртывании в другом окружении выполните проверку повторно.
